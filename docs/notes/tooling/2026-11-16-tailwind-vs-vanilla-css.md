## 结论

分三种情况：

| 场景 | 选择 |
| --- | --- |
| 用现成的文档框架，界面只需微调 | **框架自带主题 + CSS 变量** |
| 需要完全自定义的界面，且代码由人逐行审阅 | 原生 CSS 或 CSS Modules 都行 |
| 需要完全自定义的界面，且代码主要由模型生成 | **工具类（Tailwind）** |

本站属于第一种，所以最终没有引入 Tailwind。

## 推导

### 判断标准：一次改动的影响范围

原生 CSS 的核心风险不是写起来麻烦，而是**全局层叠**。改一条 `.card` 规则，可能同时影响列表页、详情页和 404 页——而且不会报错，只有打开对应页面才能发现。

工具类没有这个问题：`px-4` 只作用于当前元素，改动是局部的、可预测的。所以只要「代码没人逐行审阅」，工具类的收益就很大。

### 但文档框架已经把这层做完了

VitePress 这类框架自带导航、侧边栏、目录、搜索框、暗色模式和正文排版。它们不是「几个组件」，而是一整套调好的样式系统，通过 CSS 变量暴露定制点：

```css
:root {
  --vp-c-brand-1: #185fa5;
  --vp-font-family-base: 'Noto Sans SC', system-ui, sans-serif;
}
```

这时候再引入 Tailwind，会得到三个负面结果：

1. **能力重叠**：布局和间距工具类只能用来写新组件，而站点里几乎没有新组件。
2. **预检冲突**：工具类的样式重置会清掉标题、列表、引用的默认样式，正文排版反而要重新修。
3. **维护面翻倍**：框架升级要适配一次，工具类升级再适配一次。

代价大于收益。只有当你决定放弃自带主题、从零写界面时，前两条才不成立。

### 反过来说，什么时候必须上工具类

一旦需要自己实现卡片、标签、分页这些组件，命名漂移的问题就会出现：同一个「笔记卡片」可能被写成 `.card`、`.note-card`、`.post-item`，后期无法统一改版。

工具类的词表是封闭的，`flex`、`items-center`、`gap-4` 只有一种写法，而且构建只输出实际用到的类，不会逐年累积无人敢删的死规则。

## 易错点

- **以为用了工具类就不用管正文排版**。长文有几十种元素，逐个写工具类不现实，仍然需要 `prose` 这类排版层。
- **在没有设计系统的情况下直接改主题变量**。先定 3 到 5 个颜色和一套字号，再动 CSS，否则会变成到处打补丁。
- **把框架的 CSS 变量写进组件作用域**。变量定义在 `:root` 才会被整站继承，写在组件里只影响组件自身。
